# PaxoInsight Standalone 6.1 — проверка безопасности

Дата: 20 октября 2026 года.

**Вывод: найденную готовую Standalone-сборку нельзя считать прошедшей аудит
Web-версии. Для работы с недоверенными архивами рекомендован отдельный
исправленный выпуск.** Подтверждены проблемы доступности и обработки данных;
выполнение произвольного кода, чтение локальных файлов через XXE и выход записи
за рабочую папку данной проверкой не доказаны.

Код приложения, EXE, ZIP, настройки и GitHub не изменялись. Добавлены только
этот отчет и материалы проверки. Документ — техническая оценка, не сертификат ИБ.

## 1. Что проверено

Изучен [исходный аудит Web](SECURITY_AUDIT_2026-10-20.md). Его команды развертывания
не выполнялись: они не являются частью запроса на проверку Standalone.

Проверены отдельно:

1. Готовый `dist/PaxoInsight_v6.1_Python314_Portable.zip` от 12 октября.
2. Совпадающий с ZIP файл `dist/python314/PaxoInsight/PaxoInsight.exe`:
   содержимое PyInstaller/PYZ и нативные библиотеки комплекта.
3. Текущие исходники настольного интерфейса, общего архивного ядра, анализаторов,
   отчетов и Windows-сборки, включая изменения из Web-аудита.
4. 14 зависимостей из исходного `SBOM.cdx.json` по базе pip-audit.

Идентификация готовой сборки:

| Объект | SHA-256 |
| --- | --- |
| Portable ZIP, 22 758 170 байт | `84ca59066e9e06978a20462c9a0a4938804e88950a0e397f0f6225d20ceb6b62` |
| EXE в ZIP и в распакованном каталоге | `5bfd7480edd11b5b44ae9eb54bce559f7cc27b593390c2196dc2e032a77dbf51` |

ZIP: 166 записей, 46 280 757 байт суммарного несжатого содержимого, проверка CRC
успешна. Хеши текущих настольных исходников закреплены в
[identity.json](standalone-security-2026-10-20/identity.json).

**Существенное различие:** EXE содержит старый модуль `PaxoInsight` и прежние
обработчики распаковки. В нем отсутствуют `paxoinsight.archive_io`,
`paxoinsight.analysis_inputs`, `paxoinsight._vendor.analyzers` и `defusedxml`.
В текущих исходниках эти усиления есть. Одинаковая надпись «6.1» не означает
одинаковое состояние безопасности. Даже файлы из `build/lib` не приняты за
точный источник EXE: их полное совпадение с встроенным кодом не подтвердилось.

## 2. Основные находки

Уровни ниже — приоритет исправления для этого приложения, не официальные
CVSS-оценки и не количество независимых CVE.

### S-01 — высокий: исчерпание памяти при распаковке ZIP на Python 3.14.7

В комплекте находится `python314.dll` версии **3.14.7**. Для `zipfile` известна
ошибка **CVE-2026-15310**: некоторые декодеры выделяют большой буфер до ограничения
выхода. Она исправлена в Python 3.14.8.
[Описание CPython](https://github.com/python/cpython/issues/156002),
[официальный выпуск 3.14.8](https://www.python.org/downloads/release/python-3148/).

Безопасно воспроизведен ограниченный вариант: ZIP/BZIP2 с заявленным размером
32 байта и правильной CRC этих 32 байтов проходит проверку размеров, но декодер
сначала возвращает **16 777 216 байт одним буфером**, затем результат обрезается.
Файл на диске имеет 32 байта, поэтому счетчик записанных байтов сам по себе
этот расход памяти не замечает. Масштабирование до исчерпания памяти рабочего
компьютера намеренно не выполнялось.

Проверка использовала реальные данные ZIP, не подмененный список записей.
Инструментальная обертка только записывала размер результата декодирования.
Код `ZipExtFile._read1` совпал с встроенным в EXE; SHA-256 `python314.dll` и
`_bz2.pyd` в тестовом интерпретаторе и комплекте EXE также совпали.

**Статус:** воспроизводится и с кодом EXE, и с текущим ядром, если запускать его
на имеющемся Windows Python 3.14.7. Пересборка текущими инструментами без
обновления Python не решит проблему.

**Исправление:** поддерживаемый исправленный CPython 3.14, не ниже 3.14.8;
повторная проверка встроенной стандартной библиотеки и DLL. Защита памяти
дочернего процесса полезна дополнительно к исправлению Python.

### S-02 — высокий: неполные ограничения распаковки в готовом EXE

Подтверждено на малых примерах:

- при `max_files=3` TAR с пятью пустыми каталогами принят;
- при том же лимите принят ZIP с одним файлом и четырьмя неявными каталогами;
- обработчик 7Z при смоделированном ложном списке размеров записал 4096 байт
  при лимите 32 байта; проверен именно этап записи, не только итоговый обход;
- обработчик ZIP продолжил запись при смоделированном нулевом свободном месте.

Сценарий с 7Z — проверка через подмену `list()` в тесте, а не доказательство
существования конкретного вредоносного 7Z с такими заголовками. Она подтверждает
отсутствие собственной проверки фактической записи. py7zr 1.1.3 имеет свою
защиту, но EXE не передает ей лимит текущего задания и не использует ограниченный
writer. Итоговая проверка после извлечения не предотвращает предварительный
расход диска/ресурсов. У RAR нет текущего периодического контроля дерева и диска;
ожидание процесса ограничено тайм-аутом, но отмена пользователем не проверяется
внутри этого ожидания. Создание итогового 7Z также выполняется без нового
`GuardedArchiveOutput`.

**Статус:** соответствующие проверки архивов в текущем общем ядре усилены;
в имеющемся EXE их нет. Нужна новая сборка и повторная проверка именно ее,
включая сохранение суммарных лимитов при вложенности.

### S-03 — средний: пароль RAR передается через командную строку процесса

Старый `_extract_rar` формирует аргумент `-p<пароль>` и вызывает 7-Zip.
Это подтверждено перехватом запуска с синтетическим паролем. Такая строка может
попасть в средства наблюдения за процессами и журналы EDR; доступ к ней зависит
от прав и конфигурации Windows. Маскирование поля интерфейса этого не устраняет.
Утверждение о гарантированном отсутствии пароля вне памяти приложения для
готовой сборки некорректно. `shell=False` используется — инъекция команд shell
этим тестом не обнаружена.

**Статус:** текущий исходник передает пароль через stdin; проверка это подтвердила.
Также добавлены принудительный выбор RAR3/RAR5, `--` и периодическая отмена.
В новом EXE нужно повторно проверить настоящие зашифрованные RAR, включая
заголовки. Сетевой перехват и запись реальных паролей не выполнялись.

### S-04 — средний: незаметная перезапись одинаковых путей в архиве

ZIP и TAR с двумя записями `same.txt` приняты EXE; после распаковки осталась
только вторая версия. Это нарушение однозначности и целостности комплекта,
не доказательство перезаписи произвольного файла вне рабочей папки.

**Статус:** текущий writer с режимом `xb` отклоняет дубли; оба синтетических
примера завершились `FileExistsError`. Исправление отсутствует в старом EXE.

### S-05 — средний: XML и метаданные старого анализатора не усилены

Встроенный старый анализатор использует `xml.etree.ElementTree` и отдельные
неограниченные `read()`/`json.load()`. Небольшой XML с внутренней DTD/сущностью
принимается; текущий `parse_xml` отвергает его как `DTDForbidden` и ограничивает
размер метаданных. Это **не** подтверждение XXE-чтения локальных файлов:
стандартный Expat не следует автоматически считать выполняющим такие обращения.

Упакованный `pyexpat.pyd` сообщает **Expat 2.8.2**. В последующих версиях есть
исправления безопасности, включая квадратичную обработку атрибутов
CVE-2026-66046/CVE-2026-76641 и исправления UTF-16. Применимость каждого
низкоуровневого сценария отдельно не воспроизводилась.
[Changelog Expat](https://github.com/libexpat/libexpat/blob/R_2_8_5/expat/Changes).

**Исправление:** перенос усиленного анализатора и ограничений чтения в комплект
вместе с обновленным Python/Expat. Одного запрета DTD недостаточно для объявления
всех ошибок нативного парсера устраненными.

### S-06 — средний: копирование входной папки требует дополнительного ограничения

В `_copy_directory` и старой, и текущей реализации считаются файлы, но каталоги
создаются без раннего ограничения и не проверяется свободное место перед записью.
Прямой тест с лимитом 3 успел скопировать пять каталогов без исключения.
Текущее ядро отвергает превышение при последующей проверке всего дерева,
но ресурсы к этому моменту уже потрачены. Глобальная обработка пути папки
не эквивалентна ограниченному writer архивов.

**Исправление:** общий бюджет файлов, каталогов, фактических байтов и свободного
места непосредственно на этапе копирования. Это оставшаяся задача в текущем
исходном коде, не только необходимость пересобрать старый EXE.

### S-07 — риски хранения и цепочки поставки

- При обычном завершении тестовые рабочие папки очищались. При аварии или
  принудительном прекращении процесса нет гарантированной очистки расшифрованных
  временных файлов и механизма гарантированного восстановления очистки.
  Web-правило «10 минут» к Standalone не относится. Удаление не является
  физическим стиранием, а отсутствие базы не означает отсутствия файлов на диске.
- Весь разбор выполняется с правами пользователя; отдельной песочницы,
  Windows Job Object с лимитами памяти/процессов и аналогов Docker cgroup нет.
  Это эксплуатационное ограничение, не доказанная эскалация привилегий.
- EXE имеет статус Authenticode `NotSigned`. Это риск происхождения/подмены,
  не свидетельство наличия вредоносного кода.
- Windows lock-файлы фиксируют версии, но `setup_python314.ps1` устанавливает их
  без обязательной проверки хешей. Скрипт сборки проверяет только ветку 3.14,
  а не минимальную исправленную patch-версию.
- Исходный SBOM описывает 14 Python-зависимостей, но не полный состав PyInstaller,
  нативных DLL, Tcl/Tk и встроенных копий пакетов. В EXE присутствует `setuptools`.
  Текущему исходному коду дополнительно нужен `defusedxml`, которого в старом
  `SBOM.cdx.json` нет. Обновлять SBOM нужно под конкретный новый артефакт.
- 7-Zip выбирается по переменным среды, расположению приложения, PATH и системным
  каталогам без проверки минимальной версии. На проверенном компьютере найден
  **7-Zip 26.04**; это не подтверждает версии на остальных рабочих местах.
  Нужны доверенный путь и проверка версии.
  [Официальная история 7-Zip](https://www.7-zip.org/history.txt).

Итоговые 7Z по умолчанию не шифруются. Буфер обмена, его история и дампы памяти
находятся вне гарантии «пароль только в памяти»; нельзя очищать пользовательский
буфер без согласованной политики. Настройки исходного удаления архивов в рамках
проверки не изменялись.

| Компонент | Факт для проверенного комплекта | Оценка |
| --- | --- | --- |
| CPython | 3.14.7 | ZIP-путь S-01 воспроизведен; требуется исправленный runtime |
| Expat | 2.8.2 из упакованного `pyexpat.pyd` | Нужен переход на исправленный поддерживаемый комплект |
| OpenSSL | 3.5.7 из упакованного `_ssl.pyd`; `libcrypto-3.dll` 3.5.7 | Есть последующие исправления; TLS/QUIC-эксплуатация через Standalone не установлена |

| 7-Zip | внешний 26.04 | В portable ZIP не включен, зависит от рабочего места |

Для OpenSSL сведения об исправлениях проверены у
[поставщика](https://www.openssl-library.org/news/vulnerabilities-3.5/).
Наличие старого OpenSSL не объявляется доказанной удаленной атакой на приложение,
которое не предоставляет TLS-сервер.

Для zlib CVE есть [обсуждение и исправление upstream](https://github.com/madler/zlib/issues/1310),
при этом на [официальной странице](https://zlib.net/) опубликован выпуск 1.3.2.
Нельзя механически перенести спорную классификацию Debian zlib 1.3.1 из
Web-аудита на Windows DLL 1.3.2 или на встроенный zlib-ng. Статус загрузки
компонента и достижимость уязвимого API нужно учитывать отдельно.

## 5. Что из Web-аудита не переносится автоматически

HTTP/HTTPS, cookie, CSRF/Origin, роли, пользовательская SQLite, срок серверной
выдачи, защита медленных HTTP-запросов и Docker-изоляция — свойства Web-версии.
В Standalone не обнаружены упакованные FastAPI/Uvicorn и нет соответствующего
серверного сценария. Отсутствие Web-аутентификации само по себе не является
уязвимостью настольной программы: основная граница доступа — учетная запись ОС.

GNU tar и Debian-пакеты контейнера не являются компонентами найденного Windows
пакета; соответствующие контейнерные CVE сюда не скопированы.

## 6. Порядок исправления

1. Обновить Windows-среду сборки до исправленного CPython 3.14 и закрепить
   допустимую patch-версию. Не ограничиваться обновлением pip-зависимостей.
2. Закрыть ранние лимиты копирования папок; включить в новую сборку актуальное
   усиленное общее ядро, ограниченные writers и безопасный анализатор XML.
3. Проверить модульный состав **готового EXE**, DLL и поведение на атакующих
   примерах; дополнительно проверить настоящие зашифрованные RAR3/RAR5.
4. Ввести доверенный выбор 7-Zip, хеши установки desktop-зависимостей и SBOM
   всего артефакта. Рассмотреть подпись EXE/релиза.
5. Добавить безопасную политику аварийной очистки и отдельный ограниченный
   процесс анализа. Не удалять произвольные Temp-папки по одному имени.
6. Выпустить отдельное обновление безопасности с новыми контрольными суммами,
   не заменять содержимое уже опубликованного ZIP под старым хешем.

До исправления: не запускать от администратора, для неизвестных архивов
использовать изолированную VM/ограниченную учетную запись, хранить данные и Temp
на защищенном носителе, контролировать диск и не запускать извлеченные программы.
PaxoInsight не заменяет антивирус, SAST или безопасную среду исполнения.

старые протоколы.

но сторонние модули берут из существующего окружения сборки. Это не полное
инструментирование GUI-процесса. Для RAR-запуска, недостатка свободного места
и ложного списка 7Z явно использованы тестовые подмены. Полный fuzzing нативных
декодеров, длительная нагрузка, политика EDR/Defender, ACL всех рабочих мест,
резервные копии и остатки данных на носителе не проверялись. Результат не
исключает неизвестные ошибки.
