# Kotlin → .class: проценты и повышение точности в 6.1.3

Дата: 21 октября 2026 года. Локальный Windows portable-кандидат, Python 3.14.8.

## Что означают проценты

В интерфейсе, заключении, HTML/TXT/JSON показаны два числа:

- **Оценка покрытия**: подтверждённые и предположительные однозначные связи.
- **Подтверждённая доля**: только структурно подтверждённые связи при уверенном
  разборе исходника. Если разбор исходника неполон, его связи не повышают эту долю.

Это доли сопоставления Kotlin-исходников с ожидаемыми JVM-артефактами, а не
покрытие строк, методов, тестов, уязвимостей или правил SAST. Оценочный процент
не является статистической вероятностью корректности и не доказывает, что
байткод собран именно из переданной версии исходников.

### Формула

Каждый применимый `.kt` имеет одинаковый вес. Для каждого файла:

```text
доля файла = число сопоставленных ожидаемых объявлений/артефактов
            / число всех распознанных ожидаемых объявлений/артефактов

процент = 100 × сумма долей файлов / количество применимых файлов
```

Для оценки засчитываются статусы `confirmed` и `probable`, для подтверждённой
доли — только `confirmed`. Неоднозначные, отсутствующие и непроверенные связи
не засчитываются. В multifile учитываются связи конкретного исходника с его
частью и общим фасадом; это не счётчик уникальных бинарных файлов.

Например, один исходник сопоставлен полностью, у второго найдены два класса
из четырёх: `(1 + 0,5) / 2 = 75%`. Так второй файл не выдаётся за полный.
Это намеренно не равнозначно проценту по глобальному числу классов: каждый
исходник имеет одинаковый вес, независимо от размера файла и числа объявлений.

Если половина связей подтверждена, а остальные только предположительные,
оценка может быть 100%, а подтверждённая доля — 50%. Оба числа видны одновременно.

### Неопределённость

- Gradle/другие `.kts`, известные не-JVM наборы и файлы без самостоятельных
  JVM-объявлений исключаются из знаменателя.
- Неразобранный применимый исходник остаётся в количестве файлов, но даёт
  нулевой вклад. Это консервативный расчёт, **не доказательство отсутствия классов**.
- Если не распознано вообще ни одного ожидаемого объявления, выводится **«н/д»**,
  а не вымышленные 0% или 100%.
- Основной код и тесты имеют отдельные показатели; общий процент включает оба.
- Нераспакованные контейнеры, повреждённый/ограниченный разбор и неоднозначность
  помечают оценку неполной; показывается число неопределённых исходников.
- Старые эвристические результаты могут давать только оценку, не подтверждённую долю.

Значение JSON хранится в `analysis_data.kotlin_mapping.coverage`, метод
`file-weighted-declaration-fraction-v1`. Числа округлены до одного знака.
Индекс и проценты существуют только для текущего задания; повторный анализ
пересчитывает их, следующее задание сбрасывает.

## Что улучшено в точности

1. **Строки.** Вложенные `${...}` с собственными строками, комментариями и скобками,
   raw- и multi-dollar-шаблоны читаются как один строковый токен. Их содержимое
   не создаёт ложные объявления; обычные шаблоны больше не понижают уверенность
   автоматически. Вложенность ограничена, выражения не вычисляются.
2. **JVM-аннотации.** Поддержаны import-алиасы `JvmName` и `JvmMultifileClass`,
   fully-qualified имена и Kotlin escape-последовательности строковых литералов.
   Вычисляемые константы по-прежнему не исполняются.
3. **Конструкторы.** Лямбда в значении параметра больше не теряет контекст
   содержащего класса: следующие вложенные объявления распознаются правильно.
4. **Выходы Multiplatform.** Распознаётся корень
   `build/classes/kotlin/<target>/<compilation>`; цель JVM/Android и набор исходников
   не смешиваются. Основной код, unit-тесты, fixtures и instrumentation разделяются.
5. **Коллизии.** Один class-файл из неизвестной структуры не может подтвердить
   несколько разных исходников. Такие связи становятся неоднозначными и не
   повышают процент. Настоящий общий multifile-фасад — намеренное исключение.
6. **Имена фасадов и противоречия.** Если имя фасада не задано литералом,
   фактическое имя уточняется по `SourceFile`, пакету и виду Kotlin Metadata.
   Это учитывает нормализацию имён компилятором, не вычисляя пользовательские
   выражения. Явное несовпадение `SourceFile` или вида Metadata не засчитывается
   даже приблизительно; отсутствие этих сведений и противоречащие сведения
   больше не считаются одинаковой ситуацией.

Полные Kotlin AST, protobuf d1/d2, DEX, SMAP, семантика методов и доказательство
тождественности сборки всё ещё не реализованы. Нестандартные плагины, roots,
обфускация и сложные компиляционные сценарии могут оставлять неопределённость.

## Что целесообразно делать дальше

| Вариант | Польза | Сложность / ограничение |
| --- | --- | --- |
| Полный синтаксический Kotlin-парсер | Более надёжные объявления и контекст для редких конструкций | Грамматика и версии Kotlin, новые зависимости/wheels и проверка Python 3.14 |
| Полный разбор Kotlin Metadata d1/d2 | Более точная модель объявлений, JVM-сигнатур и фасадов | Версионность BitEncoding/ProtoBuf; чистый Python требует отдельного ограниченного декодера и большого набора реальных fixtures |
| ASM + официальный kotlin-metadata-jvm в доверенном helper-процессе | Использование официальной модели метаданных | Добавляет Java/JRE, размер portable, обновления и SBOM; классы нужно читать как данные, не загружать через Class.forName |
| Манифест доверенной CI-сборки | Проверка конкретной пары исходников и бинарных файлов по хешам | Требует доверенной сборочной стороны; наличие одноимённого файла само по себе ничего не доказывает |

Для самостоятельного приложения следующим содержательным шагом предлагается
расширенный синтаксический разбор и затем ограниченный version-aware decoder
Metadata. В этом обновлении тяжёлые зависимости и Java не добавлялись.
Автоматически выполнять Gradle/Maven из неизвестных архивов не предлагается.

## Проверка и воспроизведение

[Тесты](kotlin-coverage-6.1.3-2026-10-21/tests-source.txt),
[настоящий Kotlin и Tk-виджеты](kotlin-coverage-6.1.3-2026-10-21/kotlin-verification.json),
[пример HTML с процентом](kotlin-coverage-6.1.3-2026-10-21/kotlin-example-partial.html).

Проверяются случаи 75%, 100%/50%, н/д, непроверенные файлы, раздельные main/test,
коллизии, aliases, templates и цели компиляции. На настоящих Tk-виджетах проверяются
50% → 100% при повторном анализе и сброс при следующем задании.
Официальные Kotlin stdlib JAR используются только как тестовые данные,
не исполняются и не входят в portable; их происхождение и границы проверки
описаны в предыдущем документе структурного анализа.

```powershell
cd C:\Paxo\PaxoInsightApp
C:\Paxo\.venv3148\Scripts\python.exe -m unittest discover -s tests -p "test_kotlin*.py" -v
pwsh -NoProfile -File build\build_windows.ps1 -BuildVariant kotlin-6.1.3
```

Правила проверены по первичным источникам:
[строки Kotlin](https://kotlinlang.org/docs/strings.html),
[import aliases](https://kotlinlang.org/spec/packages-and-imports.html),
[Multiplatform compilations](https://kotlinlang.org/docs/multiplatform/multiplatform-configure-compilations.html).

Ранее отмеченные ограничения безопасности Standalone не объявляются устранёнными
добавлением процентов. Это локальный кандидат для проверки на рабочих материалах.
